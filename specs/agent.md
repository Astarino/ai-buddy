# Поведение агента и контракты инструментов

Версия промпта: `buddy-grounded-v4`. Требования ниже задают поведение реализации.

## Ответы

1. Сервер определяет пользователя по непрозрачной cookie тестовой сессии, а не по тексту или переданному `user_id`.
2. Права проверяются до поиска. Ранжируются только доступные документы своей команды и общие материалы. Контекст ограничен тремя короткими документами.
   Если пользователь явно выбрал общий или Backend-чек-лист, используется этот лист. При просьбе сравнить оба листа доступны оба; сроки и роли не смешиваются.
3. Модель получает вопрос, краткую разрешённую историю, команду, текущий этап и документы с ID. Документы и история — данные, не инструкции. У модели нет SQL, shell, сети или права изменить роль.
4. Ответ модели имеет схему `{answer, source_ids, needs_clarification}`. Сервер проверяет типы, длину и принадлежность каждого источника перед отображением. Неподтверждённый ответ не маскируется под успешный.
5. При нехватке сведений — уточнение или черновик вопроса наставнику. Нельзя выдумывать сроки согласования и утверждать выполнение действия.
6. Направление приходит из доверенного профиля. Backend — демонстрационный пример; вопросы не ограничены чек-листом. Ошибка доступа без однозначного ресурса требует уточнения. Ошибка GitHub не создаёт заявку на Confluence.
7. Ответ обычно содержит ближайший шаг и одно короткое объяснение. Детали операции остаются в карточке. Уточнение задаётся по одному; уже сообщённые сведения не запрашиваются повторно.
8. Сервер хранит зависимости ответа от всех документов и разрешённой истории, переданных модели, независимо от `source_ids`. После генерации и перед повторной выдачей проверяются доступ и снимки этих источников. При отзыве, изменении или недоступности проверки закрытый ответ не выдаётся. Старый модельный ответ без серверных зависимостей требует нового вопроса.
9. Запрещённые сообщения не входят в модельную историю. Секретный ввод заменяется безопасной отметкой до сохранения; повтор ID сверяется по отпечатку запроса. Служебные зависимости и отпечатки не передаются в браузер и модель.
10. Описание команды, ошибки и текущего шага от пользователя можно сопоставлять с документацией. Это сообщённые пользователем наблюдения, а не основание для изменения прав или корпоративных правил. Нельзя игнорировать уже названный путь/инструмент из-за запрета выдумывать факты.
11. Модель получает компактные источники с временными ID. Служебные поля ACL, resource ID, URL загрузки и хеши остаются на сервере. Схема Ollama ограничивает цитаты переданными ID; ответ любого провайдера переводится обратно только по серверной таблице. При внешнем inference также исключаются этап и происхождение из внутреннего каталога.
12. Если источник содержит точное значение, ответ использует его. Отсутствие факта не позволяет придумывать запрет или отсутствие ресурса. При сообщённом конфликте документов нужно уточнить, какие сведения расходятся. Предупреждение об историческом источнике не заменяет полезный ответ по его содержимому.
13. Неполное описание ошибки/настройки и сообщённое противоречие источников уточняются до модели. Публичный документ по явно названному материалу можно показать короткой дословной выдержкой. Код Jira-проекта извлекается из разрешённого командного описания, а не угадывается моделью. Эти ответы имеют kind=source и не считаются inference.
14. Если модель сама сообщает об отсутствии сведений, но не задаёт уточнение, сервер не выдаёт придуманное объяснение отсутствия ресурса. Он возвращает безопасный уточняющий вопрос и фиксирует срабатывание проверки. Это узкая проверка признанной нехватки сведений, не универсальная проверка фактов. Отчёт eval отдельно сохраняет исходный модельный ответ и вид ответа, показанный пользователю.

Рабочие команды «показать маршрут», «запросить доступ», «взять первую задачу» обрабатывает ограниченный серверный workflow. Короткие отдельные вопросы «что делать» и «что мне делать» показывают ближайший шаг маршрута без inference. Упоминание «что делать дальше» внутри вопроса об инструменте не заменяет его ответом о маршруте. Модель объясняет материалы; решение о правах и выполнении операции всегда принимает Go-код. Это сознательное ограничение полномочий маленькой модели.

## Инструменты

| Инструмент | Вход | Результат и ограничения |
| --- | --- | --- |
| `search_knowledge` | вопрос, серверный контекст | до 3 доступных документов; ACL проверен до ранжирования |
| `get_route` | серверный контекст | шаги, зависимости и следующий доступный шаг |
| `prepare_action` | `kind: access/issue`, обоснование | точные параметры из серверного каталога, ID, срок 15 минут; без побочного действия |
| `confirm_action` | ID подготовленного действия | только владелец, актуальные права, неизменяемые параметры; результат HTTP-сервиса |
| `refresh_operations` | серверный контекст | только собственные результаты; права и маршрут обновляются по состоянию сервиса |
| `complete_task` | ID шага | только доступные шаги с самоотчётом; подтверждаемые сервисом шаги менять нельзя |
| `search_public_docs` | тема Go/Git и вопрос | свежие официальные снимки; ранжирование внутри backend, произвольные URL запрещены |
| `prepare_request` / `send_request` | тема, передаваемый текст, тип получателя | доверенный адресат и отдельное подтверждение; личный чат не копируется |
| `reply_request` / `decide_access` | ID и версия | только текущий участник; согласование по реальному результату HTTP-сервиса |
| `draft_mentor_question` | вопрос | сохранённый черновик с препятствием и контекстом; без отправки |

Все ID и входы валидируются. Клиент не выбирает согласующего и не передаёт произвольный ресурс. Подтверждение не может быть создано текстом модели. Параметры, отличающиеся от подготовленных, требуют новой карточки.

## Состояния действия

`ready → completed` либо `ready → superseded`. Совпадение всех параметров возвращает ту же карточку; изменённые параметры создают новую и делают прежнюю недоступной для отправки. При технической ошибке карточка остаётся доступной для проверки/повтора с тем же ключом идемпотентности. Истечение 15 минут запрещает новую отправку; уже выполненная операция читается повторно независимо от истечения. Замена карточки не отменяет созданную операцию.

Заявка доступа: `pending → approved → granted`; `pending/approved → rejected`; `granted → revoked`. Только `granted` даёт чтение. Задача Jira: `assigned → done`. Идентификатор, владелец, ресурс и тип операции не меняются при обновлении статуса.

## Сбои

Сервис хранит операцию по ключу до ответа. При потере ответа повтор запроса с тем же ключом возвращает тот же результат. Сбой сервиса не удаляет историю и карточку. Неизвестный исход явно отображается как техническая неопределённость; он не завершает задачу. Недоступность или непригодный ответ модели возвращаются отдельно как `model_unavailable`, без совета проверять заявку, которую пользователь не отправлял. Повтор вопроса использует прежний ID. Ошибки модели не переключают провайдера. Тайм-аут и отмена освобождают слот генерации.

## Модельный набор

50 фиксированных случаев: 15 вопросов по знаниям, 10 неизвестных/уточнений, 10 прав и injection, 10 операций, 5 сбоев. Отдельно измеряются поиск, схема и допустимость источников, факты, решения workflow и запреты. Цель — не менее 90% и ноль нарушений прав/неподтверждённых действий. Прогон с фикстурой проверяет приложение и не считается проверкой Qwen.
