# Проверка

Поведение описано до реализации в `specs/product.md`, `specs/agent.md` и `specs/security.md`. Корпус и эталоны находятся в `internal/buddy/corpus.json` и `evals/`. Командные данные синтетические.

## Автоматические проверки

Нужен PostgreSQL и отдельная тестовая база. Тесты создают собственные временные схемы и удаляют только их; рабочие данные не очищаются. Не указывай production-базу.

```sh
createdb ai_buddy_test
make test
make coverage
```

Для другой среды задай `TEST_DATABASE_URL`. CI использует изолированный PostgreSQL 16.14. Если переменная не задана при прямом `go test`, интеграционные тесты пропускаются; `make test` и `make coverage` задают её явно. Успешная сборка сама по себе не считается проверкой сценария.

Проверяются: ACL до модели, чужие документы и карточки, неизменяемые параметры, TTL, идемпотентность, согласование без выдачи, отзыв во время генерации, история после отзыва, потерянный ответ после записи, ошибки JSON, недоступность сервисов, конкурентные записи, cookie и Origin, маршрут и основные состояния UI. Поддельные зависимости применяются для намеренных ошибок; сохранение и транзакции проверяются на настоящем PostgreSQL.

| Требования SDD | Основные проверки |
| --- | --- |
| S01–S04 | `TestAccessToFirstTaskJourney`, `TestHTTPJourneyAndPersistedState`, `App.test.tsx` |
| S05–S07 | `TestLostResponseAndIdempotentCorporateContract`, `TestActionExpiryAndRecovery`, `TestServiceUnavailableFailsClosed` |
| S08–S09 | путь до `CAT-101`, отдельное событие завершения, запрет самоотчёта вместо сервисного результата |
| S10–S11 | `TestChatValidationClarificationAndIsolation`, настоящий модельный набор, источник и черновик в UI |
| S12–S15 | проверки чужой сессии, закрытых метаданных, отзыва, неверного JSON, доступности UI во время генерации |
| S16–S20 | `security_test.go`: повтор после отзыва, пустые/публичные цитаты, история, неизвестный Scope и редиректы |
| S21–S22 | новая карточка, запрет старого подтверждения, GitHub 403, аналитический вопрос вне чек-листа |

OIDC проверяется локальным провайдером с настоящей тестовой RSA-подписью: PKCE, issuer/audience, подпись, nonce, срок, отсутствие ID token и повтор callback. HTTP-тесты проверяют Secure `__Host-` cookies, привязку сессии, отключение демо-входа и пульта. Проверки авторизации подменяют субъект/ресурс/действие и имитируют отказ/недоступность. Отдельно проверяются атомарность аудита, одноразовое состояние входа, подтверждение внешнего вопроса и фактическое отсутствие закрытых полей в HTTP payload модели. Сетевые тесты используют локальные ловушки или тестовый transport; корпоративные данные не отправляются наружу.

## Покрытие строк

`make coverage` формирует:

- `coverage/go.out` и `coverage/go.html`: исходный Go-отчёт. Стандартный Go считает **statements**, это отдельная метрика.
- `coverage/go.lcov`: покрытие исполняемых строк через **gcov2lcov v1.1.1**, преобразующий инструментированные Go-блоки и исходники в LCOV. Это воспроизводимая производная метрика, а не переименованный процент statements.
- `web/coverage/`: V8/Vitest, HTML, LCOV и JSON по frontend.
- `reports/coverage/`: компактный отчёт и оба LCOV для сдачи.

Порог — не менее 85% строк отдельно для backend и frontend. Между языками ничего не усредняется. Также проверяются frontend statements/functions/branches. Включены написанные entrypoint-файлы, адаптер модели и имитация, даже если их отдельное покрытие ниже среднего. Нет исключения кода по причине его написания ИИ. Тесты, зависимости и типы без исполняемых операторов не входят в знаменатель. CSS и декларативная SQL-схема не инструментируются этими счётчиками; они проверяются реальным рендером и PostgreSQL.

Конвертер: [gcov2lcov](https://github.com/jandelgado/gcov2lcov). Путь к его CLI и версия закреплены в скрипте. Исходный Go-отчёт сохраняется, чтобы методику можно было проверить независимо.

## Настоящая модель

```sh
RUN_MODEL_EVAL=true TEST_DATABASE_URL='postgres:///ai_buddy_test?host=/tmp' \
  go test ./internal/buddy -run '^TestRealModelEvaluation$' -count=1 -v -timeout=20m
```

Нужен запущенный проверенный Ollama и загруженная Qwen. Можно задать `EVAL_MODEL_BASE_URL` и `EVAL_MODEL_NAME`; новая конфигурация требует нового отчёта. Прогон выполняет 50 случаев: 15 вопросов по знаниям, 10 неизвестных/уточнений, 10 прав/injection, 10 операций и 5 сбоев. Результаты, число **реальных вызовов inference** и время каждого случая записываются в `reports/model-evaluation.json`. Серверные операции не притворяются ответами модели. Намеренно повреждённая зависимость также помечена отсутствием inference.

Набор служит инженерной проверкой и использовался при исправлении поведения. Это не независимое исследование людей и не оценка всех возможных вопросов. Цель: ≥90%, ноль нарушений прав и неподтверждённых операций. Описания ранних проблем и параметры находятся в `docs/model.md`.

## Сквозной HTTP-путь

```sh
python3 scripts/smoke.py http://127.0.0.1:8090
```

Скрипт проходит вход, запрет чужого документа, подготовку/подтверждение, повтор, отдельное согласование, выдачу, чтение руководства и назначение первой задачи. Результаты остаются в БД. Повторный прогон сверяет существующие операции. `SMOKE_PROFILE=irina` выбирает вторую команду. Пульт использует тестовый `DEMO_OPERATOR_TOKEN`; скрипт не работает с настоящими корпоративными сервисами.

## Браузер

```sh
make e2e
```

Команда создаёт временную схему PostgreSQL и отдельные серверы с явно помеченным fixture-провайдером. Рабочая база не меняется. Playwright проходит восемь проверок на desktop 1440×900 и mobile 390×844: полный путь до Jira, изоляция сессий, маршрут с клавиатуры, поиск источников и восстановление потерянного ответа без повторной отправки. На macOS используется установленный Chrome; CI устанавливает Chromium отдельно.

Покрытие собирается с race detector и без кеша тестов, чтобы не смешивать блоки разных версий исходников. В сборку входят `cmd` и `internal`; служебные скрипты в игнорируемом `tmp` не меняют состав проверяемого приложения. Отдельно проверяется одновременный старт восьми подключений к пустой схеме PostgreSQL. Точные результаты текущей проверки находятся в [reports/coverage](../reports/coverage/summary.json); Go statements — отдельная метрика. Старые модельные отчёты относятся к `buddy-grounded-v2`, а не к текущему промпту v3.

Вручную просмотрены desktop и mobile, источник и диалог подтверждения. Axe-core 4.12.1 по WCAG 2 A/AA не нашёл автоматических нарушений в основном экране обеих ширин; проверки контраста скрытых при прокрутке элементов остались incomplete. Это не сертификация доступности и не исследование на пользователях.

## Поиск и ответственные

`requests_test.go` проверяет пять стажёров, разные проблемы, скрытый черновик,
идемпотентность, отзыв назначения, версии, владельца ресурса и конкурентные
решения. HTTP-тесты проверяют подмену получателя и чужие карточки. Хранилище
проверяет откат карточки при сбое аудита. Отдельные UI-тесты проверяют сохранение
ввода и ключа при сетевой ошибке, предварительный просмотр и два этапа доступа.

Обычный CI не зависит от публичного интернета и настоящей модели. Для свежих
официальных документов и браузерной цепочки доступны явные сетевые проверки:

```sh
RUN_PUBLIC_SEARCH_EVAL=true go test ./internal/publicdocs -run TestLiveOfficialDocumentation -count=1
RUN_LIVE_BROWSER=true make e2e
```

Снимок реального сетевого поиска находится в `reports/public-search.json`.
Он доказывает получение официальных фрагментов; это не отчёт о генерации Qwen.
